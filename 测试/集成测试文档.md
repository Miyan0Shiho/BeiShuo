## 2. 测试概述

### 2.1 测试目标

验证平台四大核心模块（用户认证、文件上传、OCR 识别、AI 阐释）协同工作的能力，确保数据在服务间准确流转，核心业务流程完整且稳定。

### 2.2 测试范围

| 集成层级            | 涉及模块                     | 测试重点                                             |
| ------------------- | ---------------------------- | ---------------------------------------------------- |
| **服务间 API 集成** | 文件、OCR、AI 服务           | 接口协议兼容、数据格式一致、异常传递                 |
| **前后端集成**      | 前端界面 + 后端 API          | 操作触发正确 API 链、数据正确渲染                    |
| **数据流集成**      | 数据库、本地文件系统、外部 API | 关键业务数据（inscription_id, file_id, text）不丢失、不错乱 |
| **业务流程集成**    | 全模块串联                   | 从“图片上传”到“获得 AI 阐释”的完整用户旅程           |

### 2.3 通过标准

1.  **核心场景**：本章第 4 节中所有 P0、P1 级场景 100%通过。
2.  **数据一致性**：跨服务的关键业务数据（如用户 ID、文件 ID）关联正确。
3.  **无阻塞缺陷**：不存在导致核心流程完全中断的 P0 级缺陷。
4.  **性能基准**：单次完整流程（登录 → 上传 → 识别 → 阐释）端到端响应时间 < 60 秒。

4. 核心集成测试场景

场景一：新用户完整旅程（端到端主流程）
测试ID：INTEGRATION_SCENARIO_01

优先级：P0

目的：验证新用户从注册到完成一次碑文识别的完整正向流程。
前置条件：所有后端服务健康。

测试步骤与验证点：

用户注册
请求：POST {{base_url}}/api/v1/auth/register
数据：{"username": "test_journey_1", "password": "Test@123456"}
验证：状态码 201，数据库 users 表存在该用户（密码为密文）。

用户登录
请求：POST {{base_url}}/api/v1/auth/login
数据：使用上一步的凭证。
验证：状态码 200，响应体包含有效的 access_token。保存该token至环境变量。

上传碑文图片
请求：POST {{base_url}}/api/v1/upload
Headers：Authorization: Bearer {{access_token}}
Body：form-data，key为 file，上传 stele_clear_sample.jpg。
验证：状态码 200，响应体包含 file_id 和 url。保存 file_id 至环境变量。

触发OCR识别
请求：POST {{base_url}}/api/v1/ocr/recognize
Headers：Authorization: Bearer {{access_token}}
数据：{"file_id": "{{file_id}}"}
验证：状态码 202 (Accepted)，表示任务已接收。

获取OCR结果 (轮询)
请求：GET {{base_url}}/api/v1/ocr/result/{{file_id}}
Headers：Authorization: Bearer {{access_token}}
验证：状态码 200，响应体包含 text（识别出的文字）和 confidence（置信度）。识别文本应包含“司徒”、“司空”等关键字。保存 text 至环境变量。

请求AI智能阐释
请求：POST {{base_url}}/api/v1/ai/interpret
Headers：Authorization: Bearer {{access_token}}
数据：{"text": "{{ocr_text}}", "instruction": "请用现代汉语解释这段碑文的内容和历史背景。"}
验证：状态码 200，响应为流式或非流式文本。内容需包含至少3个预设关键词（如“东汉”、“孔庙”、“卒史”）。

验证历史记录
请求：GET {{base_url}}/api/v1/history
Headers：Authorization: Bearer {{access_token}}
验证：状态码 200，返回的列表中存在本次操作的记录，关联正确的 user_id, file_id。

场景二：服务间数据一致性校验
测试ID：INTEGRATION_SCENARIO_02

优先级：P1

目的：验证核心业务标识在跨服务调用过程中的正确传递与严格隔离。

前置条件：场景一已成功执行，数据库中存在完整记录。

测试步骤与验证点：

用户数据隔离验证
操作：使用另一个测试用户 tester_02 的token，尝试访问 tester_01 上传的文件结果 (GET /api/v1/ocr/result/{{tester_01_file_id}})。
验证：应返回 403 Forbidden 或 404 Not Found，确保用户数据严格隔离。

ID链路追溯验证
操作：在测试数据库直接执行关联查询。
SQL示例：
SELECT u.username, f.file_id, o.text, a.session_id
FROM users u
JOIN files f ON u.id = f.user_id
JOIN ocr_results o ON f.id = o.file_id
LEFT JOIN ai_sessions a ON o.id = a.ocr_result_id
WHERE u.username = 'test_journey_1';
验证：能通过 user_id 关联查询到完整的 file_id -> ocr_text -> ai_session_id 链路，数据完整无误。

场景三：异常流与系统容错
测试ID：INTEGRATION_SCENARIO_03

优先级：P1

目的：验证当某个依赖服务异常时，系统的整体行为是否符合预期，具备优雅降级或明确报错的能力。

模拟异常点	测试方法	预期系统行为（集成层面）
OCR服务不可用	Mock OCR服务接口返回 500 或超时	前端应收到明确的任务失败状态（非200），界面提示“识别服务暂不可用”
上传非图片文件	上传一个 .txt 文本文件	文件服务应拒绝，返回 400 Bad Request，错误信息明确为“仅支持图片格式”
用户Token失效	使用一个已过期或伪造的token调用上传接口	网关或业务服务应返回 401 Unauthorized，引导用户重新登录
AI服务限流	Mock AI服务返回 429 Too Many Requests	前端应收到友好提示“服务繁忙，请稍后重试”，并有重试机制或队列
场景四：基于知识库内容的直接阐释验证
测试ID：INTEGRATION_SCENARIO_04

优先级：P0

目的：跳过OCR环节，直接验证AI服务对给定碑文原文的理解准确性和内容生成质量。

前置条件：AI服务正常，用户已登录。

测试步骤与验证点：

构造请求
请求：POST {{base_url}}/api/v1/ai/interpret
Headers：Authorization: Bearer {{access_token}}
数据：直接将《乙瑛碑》原文片段作为 text 参数，instruction 为“请进行通俗释义并介绍背景”。

自动化内容验证（Postman Tests脚本）

// 在请求的Tests标签页中执行
pm.test("AI响应包含关键历史信息", function () {
    var jsonData = pm.response.json();
    var aiResponse = jsonData.data.content.toLowerCase(); // 根据实际响应结构调整路径
    var keywords = ["东汉", "永兴元年", "孔庙", "百石卒史", "司徒", "司空"];
    var foundCount = keywords.filter(word => aiResponse.includes(word)).length;
    pm.expect(foundCount, `AI回复应至少包含3个历史关键词。实际包含: ${foundCount}`).to.be.at.least(3);
});
